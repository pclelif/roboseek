# Robot Hunt UI inspection (before integration)

1. **Scene:** User-confirmed active gameplay scene is `Assets/ThirdParty/SyntyStudios/PolygonCity/Scenes/Demo.unity` (Unity 6000.3.9f1 / URP 17.3). City environment, RobotPlayer, Main Camera, RobotThirdPersonCamera, random prop generator, Phase 4 NPC System and six aggression zones. `UI_System_Demo.unity` is the separate experimental UI reference and is not the integration scene.
2. **UI:** ObjectHuntHUD creates its Canvas and EventSystem at runtime. RobotShowcaseUI and GameModeSelectionUI render IMGUI test panels. No serialized gameplay Canvas/EventSystem. Existing framework includes UIPanel/UIWindow/UIManager; the production scene does not instantiate them. Existing SettingsUI is a runtime modal; no shared Controls implementation exists.
3. **Targets:** ObjectHuntRoundManager selects one real prefab per category from the serialized catalog, spawns with NavMesh/ground checks, publishes RoundStarted/TargetCollected/TimerChanged and completion/failure events. SelectedTargets and CollectedTargets expose state; scene catalog has no icons. One unused TeddyBear entry has a missing prefab and is excluded by existing selection.
4. **Interaction:** The same manager implements GetNearestInteractable and TryPickupNearest. Actual detection uses 5.5 m horizontal and 5 m vertical limits (not the definition's interactionRange). CollectibleTarget owns turning, gesture, travel/shrink, manager notification and network RPC. Keep these rules and animations.
5. **Player/camera/input:** RobotMovementController uses CharacterController and PlayerInputReader. Cinemachine 3 orbital camera uses ThirdPersonCameraController. InputSystem_Actions supplies Player/UI maps; reader and manager also read legacy keys directly. PlayerCombatInput drives CombatAttack. No raycast reticle is required.
6. **Cursor:** ThirdPersonCameraController writes cursor state each Update, releasing on Escape and relocking on mouse click. Legacy PauseMenuUI and UIManager also manage cursor. These cannot remain concurrent owners in the new scene UI.
7. **Round:** RoundGameLoop already owns Lobby → Intro → Targets → Countdown → Search → RoundComplete → Result, countdown events, timing and next-round control. autoStart was true. Missing public return-to-lobby/restart and input gating are minimal integration additions, not a replacement loop.
8. **Color:** RobotColorCustomizer, RobotColorPalette and RobotColorService supply theme/palette APIs and PlayerPrefs. Existing player has a palette. Reuse these APIs and preserve preferences.
9. **Reuse:** Manager target events/state, existing nearest-interactable query, loop phase/countdown/results, SettingsManager preferences, customizer/palette, input asset and real target prefabs.
10. **Do not rewrite:** Target selection/spawning, CollectibleTarget retrieval animation/network logic, movement, combat damage, NPC detection/navigation, robot animation, network systems and color implementation.
11. **Conflicts:** Duplicate old HUD/test panels; competing Escape/cursor handlers; raw key fallbacks bypass disabled action maps; pickup/attack coroutines restore movement independently; scaled countdowns would stall when the world is frozen. Existing score formulas differ: ScoreManager (if present) uses find/combat points; RoundGameLoop has its own result score. Use the scene's available score source explicitly. Existing missing WorldGenerator script remains outside UI scope.
12. **Integration:** Serialized Canvas_UI_Root in the confirmed scene; event-driven TargetHUD and round presentation; thin interaction-state adapter using the existing query; one UI state/cursor owner; component-level input gate; realtime presentation timing; shared Settings/Controls with navigation history. Preserve old UI components disabled in the gameplay scene. No scene-name-based automatic bootstrap and no modifications to the experimental scene.
